## 🎯 Модель продукта (не SaaS)

> **Обновлено:** 11.08.2026 · Подключение партнёров **только администратором**.

Сервис **не** публичный SaaS. Три роли:

| Роль | Кто | Доступ |
|------|-----|--------|
| **Админ** | Алексей | Оператор: партнёры, VPS, Пульт, доктор. **Не** сборщик на хабе |
| **Партнёр** | Клиент | Вход → заявки + Telegram. Если админу нужны заявки — онбординг как партнёру |
| **Агент (продажи)** | Находит партнёров | Вне продукта или read-only |

**Не делаем:** публичная регистрация, self-service онбординг, автоматический биллинг как SaaS.  
**Делаем:** операторская админка + VPS agent v2 на каждого партнёра.

Публичная регистрация отключена (`/api/auth/register` → 403, `/auth` — только вход).

## 🧭 Философия (незыблемые принципы)

### Золотое правило

> **Ждун должен быть НЕОТЛИЧИМ от человека. Если не может работать безопасно — лучше НЕ РАБОТАТЬ, чем спалиться и потерять аккаунт.**

Один аккаунт Profi = **актив на годы**. Потеря **необратима**. Любой код, который рискует аккаунтом, хуже отсутствия сбора.

### 10 заповедей (из `docs/ANTI_BLOCK_PLAN.md`)

| # | Принцип | Реализация |
|---|---------|------------|
| 1 | **Один IP = один аккаунт** | VPS на партнёра, не прокси-ротация |
| 2 | **Один браузерный профиль = один аккаунт** | Persistent context, куки на диске |
| 3 | **Человеческие задержки** | 3–7 мин между проверками, скролл, случайные клики |
| 4 | **Не перезаходить без нужды** | Persistent profile, вход не чаще 1 раза в 4 часа |
| 5 | **Circuit breaker** | 3 ошибки → стоп 60 мин → алерт |
| 6 | **Exponential backoff** | +2 мин → +10 мин → +60 мин |
| 7 | **Persistent состояние** | CB и кулдауны в БД/файле, не в памяти |
| 8 | **Тихий режим при ошибках** | Молчим, не спамим Profi запросами |
| 9 | **Внешний health-check** | Мониторинг не внутри ждуна |
| 10 | **Graceful degradation** | Profi упал → Kwork работает, хаб жив |

### Архитектурная философия

```
┌─────────────────────────────────────────┐
│  ХАБ (leads.konversus.ru)               │
│  Только: UI + API + БД + Telegram       │
│  НИКАКОГО Playwright для Profi          │
└──────────────────┬──────────────────────┘
                   │ HTTPS
         ┌─────────┼─────────┐
         ▼         ▼         ▼
      VPS #1    VPS #2    VPS #N
      1 IP      1 IP      1 IP
      1 Profi   1 Profi   1 Profi
      Agent v2  Agent v2  Agent v2
```

**Хаб — тонкий.** Вся «грязная» работа с браузером — **только на VPS партнёра**.

### Что НЕ делаем (никогда)

```
❌ Playwright для Profi на хабе (109.196.165.106)
❌ pm2 start leads-profi / profi-watcher на хабе
❌ Авто-рестарт при ошибке входа
❌ Больше 3 попыток входа подряд
❌ Два ждуна на один аккаунт
❌ Правки production через SSH без git
❌ Хранить состояние CB только в памяти
❌ Восстанавливать worker.ts
```

**Политика в коде:** `src/config/hub.ts` → `profiOnHub: false`

## Этап 4.9 — Единый Telegram-бот партнёра

**Дедлайн:** после успешного пилота (4.6) · **Статус этапа:** ⚪ **Запланировано**

> **Цель:** один бот сервиса (`TELEGRAM_BOT_TOKEN` в `.env`) — уведомления о заявках **и** безопасные настройки партнёра. Партнёр **не** создаёт бота в BotFather. Profi-логин, VPS, лимиты — только админ.

### Модель

Два Telegram-канала **не смешивать:** партнёр — заявки + свои фильтры; админ — ops (offline, CB, сводка, доставка в TG). Тот же `@leadskonversus_bot`, разные chat_id.

| Кто | Что настраивает | Где |
|-----|-----------------|-----|
| **Партнёр** | Часы сбора, ключевые слова, минус-слова | Только бот (`@leadskonversus_bot`) |
| **Админ** | Profi, VPS, лимит/месяц, вкл/выкл сбора, бюджет, antiDetect, интервал | Админка / Пульт |

Дашборд партнёра — **read-only** (список заявок). Фильтры в UI партнёра не дублируем в 4.9.

### Безопасность Profi (незыблемо)

- Партнёр **не** меняет: логин/пароль Profi, интервалы проверки, antiDetect, вкл/выкл сбора, VPS, бюджет.
- **Стоп сбора — только админ.** Партнёр не включает/выключает ждуна (лишний login = риск бана).
- Часы сбора: только в рамках **08:00–22:00 МСК** (min 6 ч «тишины»), по умолчанию из админки.
- Ключевые/минус-слова: лимит длины, валидация; применение на **следующем** `GET /api/v2/agent/config` (**без** рестарта Playwright, **0** новых входов Profi).
- Смена фильтров: не чаще 1 раза в 4 ч (cooldown в БД).

### 5.8 — Админ видит, что заявки реально ушли партнёру в Telegram

> Сейчас в пульте/сводке есть «заявок в БД». Этого мало: админ должен понимать, что **карточка дошла в чат партнёра**, а не только сохранилась на хабе.

| Где | Что показать |
|-----|----------------|
| **Пульт** (`/dashboard/admin/ops`) | На строке партнёра: сегодня **в БД** / **в TG** (успешный `sendLeadNotification`) |
| **Telegram админу** | Вечерняя сводка (~21:00): по каждому партнёру `имя: N в БД · M в TG`. Если M &lt; N — строка «⚠ TG не дошло» |
| **Сразу (редко)** | Первая успешная доставка партнёру за день → одно сообщение админу: `пилот / Настя: первая заявка ушла в TG`. Не чаще 1×/партнёр/сутки. Не дублировать каждую заявку |

Учёт: при отправке в `sendLeadNotification` писать счётчик (например `source.config._tgSentToday` + дата МСК, или поле/таблица delivery). Не рестартить агент. Не слать админу копии самих заявок.

**DoD 5.8:** админ по пульту и вечерней TG-сводке видит, сколько заявок получил каждый партнёр в Telegram; расхождение БД/TG видно без ручного опроса партнёра.
